Repondo
AI chatbots for B2B websites

User-flow automaton

Every state a person can be in, every event that can reach them there, the guard that decides what happens, and the state they land in. The product was built around one happy path — land, scan a site, test the widget, sign up — and every other path was undefined rather than decided. This document decides them. It is both a review artefact (what the product does today, honestly marked) and the specification the current work is being built against (see ADR 057).

Status is measured against the working tree, not against the ADR's intent: commit 9cccde9 plus an untracked api/sites/claim.js and a modified api/chat/index.js. App.jsx, Dashboard.jsx, Pricing.jsx and api/ are being edited concurrently, so partial and missing rows are the work in flight.

Identity lifecycle
Anonymous visitor → guest workspace → account, including the transfer branch

    LINK_RETURN --> TRANSFER_PROMPT: open claim, room on plan
    LINK_RETURN --> TRANSFER_AT_LIMIT: open claim, account already full
    LINK_RETURN --> REGISTERED: no claim, expired, stale, or duplicate domain

    TRANSFER_PROMPT --> REGISTERED: confirm, workspace moves
    TRANSFER_PROMPT --> REGISTERED: decline, guest copy expires on its own
    TRANSFER_AT_LIMIT --> CHECKOUT: upgrade, lead CTA
    TRANSFER_AT_LIMIT --> DELETE_CONFIRM: replace a site, destructive
    CHECKOUT --> TRANSFER_PROMPT: plan raised, claim retried
    DELETE_CONFIRM --> TRANSFER_PROMPT: slot freed, claim retried

    REGISTERED --> REGISTERED_AT_LIMIT: site count reaches the plan limit
    REGISTERED_AT_LIMIT --> REGISTERED: upgrade or delete a site
    REGISTERED --> ANON: sign out, fresh anonymous session

    GUEST_WITH_SITE --> [*]: 24h cleanup sweep deletes the workspace
    GUEST_PENDING_CONFIRM --> [*]: claim expires at 12h, workspace swept at 24h

Guests are never signed out — there is no affordance, on purpose: an anonymous session is the only key to a guest workspace, so signing out would strand it. The two terminal edges are the only ways a guest workspace ends.

§5
Magic-link return and the guest-workspace claim
Every branch of claim_guest_site(), and where each one lands the user

The claim is split across two requests made by two different sessions, and neither half is sufficient alone: create is run by the anonymous session that built the workspace, at link-send time, while it can still prove it owns the guest tenant; redeem is run after the round trip by the authenticated user and supplies nothing at all — the claim is looked up by the verified email on their own token, and the destination tenant is derived from their own user id. A claim id in localStorage would let anyone adopt anyone's guest workspace. 

stateDiagram-v2
    state redeem <>

    [*] --> LINK_SENT: claim created, email dispatched
    LINK_SENT --> LINK_RETURN: link clicked, session established
    LINK_SENT --> LINK_SENT: link expired or already used, resend

    LINK_RETURN --> redeem: POST /api/sites/claim redeem

    redeem --> REGISTERED: not_found, no claim for this email
    redeem --> REGISTERED: expired, older than 12h
    redeem --> REGISTERED: already_redeemed
    redeem --> REGISTERED: stale, site moved or deleted
    redeem --> DUPLICATE: duplicate_domain
    redeem --> TRANSFER_PROMPT: room on the plan
    redeem --> TRANSFER_AT_LIMIT: at_limit, claim stays open

    DUPLICATE --> READY: open the account's existing site, no transfer

    TRANSFER_PROMPT --> MOVED: confirm
    TRANSFER_PROMPT --> REGISTERED: decline, guest copy expires on its own
    MOVED --> READY: documents, summaries, scan jobs and leads moved with the site

    TRANSFER_AT_LIMIT --> CHECKOUT: upgrade, lead CTA
    TRANSFER_AT_LIMIT --> REPLACE: replace an existing site, secondary

    TRANSFER_AT_LIMIT --> REGISTERED: cancel, claim retryable for 12h
What moves: the site row and its documents, site_summaries, scan_jobs and leads — all in one transaction, sites last so the limit trigger sees the final state. What does not: messages. Those are the guest's own test conversations with their own draft assistant, not the new owner's customer history — and the schema agrees, since messages carries no site_id, only tenant_id and session_id, so there is no way to move just this site's.

§11
Deliberately unhandled
Transitions that exist in the space but are intentionally not implemented
Guests cannot sign out
The anonymous session is the key to the guest workspace: there is no email, no password and no other credential that could get them back in. Offering sign-out would strand the workspace for its remaining 24 hours with no way to reach it. Guests leave by saving with an email, or by letting the sweep collect it.
Test conversations do not move with a transferred workspace
messages are the guest's own experiments against their own draft assistant, not the new owner's customer history. The schema makes the same call: messages carries tenant_id and session_id but no site_id, so "move only this site's messages" is not expressible. Leads, which are business data and do carry site_id, move.
The same domain in two different workspaces is allowed
The unique index is (tenant_id, lower(domain)), not global. Two unrelated customers may legitimately both register the same domain — an agency and its client, for instance — and a global constraint would let one of them discover that the other exists.
A claim can never be redeemed with a browser-supplied id
The redeem call takes no input beyond the caller's own bearer token. A claim id or tenant id from the browser would let anyone who guessed one adopt someone else's guest workspace, which is precisely the attack the two-request split exists to prevent.
Premium has no self-serve checkout
Premium opens a mailto:. It is sold by conversation, so a Stripe price exists for the webhook to recognise but no Checkout path leads to it.
A failed theme extraction never blocks onboarding
Brand colour and org name are cosmetic. Every failure mode — captcha refusal, LLM timeout, unreachable site — falls back to the default indigo and continues. The same reasoning covers a failed page-discovery call, which falls back to indexing the single entry URL.
Parked sites are never deleted
A downgrade parks sites; it does not destroy work the customer paid to create. They stop answering and nothing else, and an upgrade restores them untouched. The limit counts owned sites, not active ones, so parking is not a way to hold eleven sites on a Basic plan.
§12
Open questions
Transitions whose target state is a judgement call, not a derivation
Should a declined transfer delete the guest workspace immediately? (#116)
Modelled here as "leave it alone; it lapses at 12h and is swept at 24h", because a decline may be a misclick and the data is still the user's own. The alternative — delete on decline — is cleaner but destroys a preview the user might return to. No decision recorded in ADR 057.
Where does a user land after "replace an existing site" during a transfer? (#120)
Modelled as: destructive confirm → delete → retry redeem → TRANSFER_PROMPT → READY on the newly moved site. It could equally land on the account's dashboard with a summary of what changed. The retry-the-claim shape is what the RPC's "leave the claim open" behaviour is built for, so that is what is written here.
Does a past-due plan gate anything? (#154)
plan_status = 'past_due' is written and read by nothing. Whether it should park sites, restrict the widget, or only show a banner is a commercial decision, not an engineering one. Left as recorded-only until someone decides.
Which site is the "current" one after a downgrade chooser? (#89)
The chooser picks which sites stay active; it does not obviously pick which one the dashboard opens on. Modelled as "the first still-active site", matching the existing activeSite fallback, but a deliberate choice would be better.
Should PAGE_SELECT survive a reload? (#63)
Marked missing rather than by-design: a site row exists at that point, so losing the selection leaves a mute assistant. Whether the fix is persisting the pending crawl or simply auto-indexing the top N pages is undecided.
